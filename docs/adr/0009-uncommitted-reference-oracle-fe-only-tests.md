# ADR-0009: Uncommitted reference oracle; Fe tests against committed expected values

**Status:** Accepted  
**Date:** 2026-11-22  
**Deciders:** Project owner

## Context

- A port of this size needs checkpoints along the way: transcript, sumcheck, relations, Shplemini, final pairing.
- Barretenberg generates a Solidity verifier for the exact circuit and tool version. It is the natural source of expected values.
- The original plan committed that verifier inside a Foundry project, together with Solidity test files: a harness exposing intermediate values, a vector generator, a negative suite run against both verifiers, a differential test with a fuzz case, and forge-std as a dependency.
- The project owner then decided that the repository must not contain Solidity and that the documentation must not contain Solidity code.
- Stage 0 began under that plan. The move described here was made the same day, 2026-11-22.

## Decision

Barretenberg's Solidity verifier is the reference oracle, but it is not committed. Tests are written in Fe against committed expected values.

| Aspect | Decision |
|---|---|
| Oracle location | `ultrahonk/.oracle/`, local and untracked, regenerated by `scripts/vectors.sh` |
| Repository contents | Fe plus a Noir circuit and scripts. No Solidity file, no Foundry project, no forge-std. |
| Tests | Every committed test is a Fe test run with `fe test`. The vault is tested with Fe tests as well. |
| Expected values | Challenges, round targets, subrelation values, scalars and the points of the final pairing are captured from the local oracle and committed as Fe constants |
| Negative tests | The revert selector of each tamper case is captured from the local oracle and committed. Fe tests assert that the Fe verifier reverts with the same selector. |
| Provenance | Stated with the constants: tool, version, how captured |
| Code size | The 24,576-byte limit is checked by a script on the built `.runtime.bin`, not by a test assertion |
| Documentation | Code samples are Fe, Noir or shell. Upstream Solidity names appear only as references to the code being ported. |

## Outcome (2026-11-23)

Carried out, except the code-size script.

| Aspect | What exists |
|---|---|
| Oracle | `scripts/vectors.sh` writes `.oracle/src/HonkVerifier.sol` and, if missing, `.oracle/foundry.toml`. Git ignores `.oracle/`. The Foundry tests that captured the values are kept locally in `.oracle/test/`; the script does not write them. |
| Repository contents | Fe, one Noir circuit, two shell scripts and the toy's Python reference (ADR-0011). No Solidity and no JavaScript file is tracked. |
| Expected values | `lib/src/vectors.fe` (challenges, public-input delta, round targets, partial pow), `lib/src/relations_vectors.fe` (the 31 subrelations and their batched value), `lib/src/opening_vectors.fe` (Shplemini scalars, consistency-check terms, pairing points, aggregation values). |
| Invalid calls | `lib/src/expected.fe`: 4 wrong proof lengths, 12 bit flips, 7 overwritten words, each of the 142 words set to `Q`, 3 changed public inputs, 3 wrong public-input counts, 4 calls that break two rules, the all-zero proof and the proof of largest values. The Fe contract reverts as the reference did on each, except for proof word 138 (ADR-0008). |
| Added coverage | One test flips the low bit of each of the 142 proof words. These flips were not all recorded from the reference, so the test asserts only that none is accepted. |
| Provenance | Stated at the top of each of those files, and in `ultrahonk/README.md`, section "The reference oracle". |
| Verification key | `scripts/proof_to_fe.sh` prints it, with the proof and the public inputs, from the raw `bb` output in `vectors/`. `--check` compares the committed constants with that output. |
| Size and gas | Measured by hand and reported next to the reference's figures in `ultrahonk/README.md`. No script checks the 24,576-byte limit. |

The tests do not show that every proof the reference rejects is rejected.

## Options Considered

### Option A: Fe-only repository with a local, uncommitted oracle (chosen)

| Dimension | Assessment |
|-----------|------------|
| Repository contents | Pure Fe plus a Noir circuit and scripts |
| Reader tooling | `fe` only |
| Fault localisation | A mismatch is located at the first step whose value differs |
| Regenerating expected values | Not possible from the repository alone; the local harness must be recreated |
| Negative coverage | A fixed list of tamper cases, each with a reference selector |

**Pros:** Meets the Fe-only requirement. Keeps step-by-step comparison with the reference.  
**Cons:** Expected values rest on documented provenance. No fuzzed comparison with the reference.

### Option B: Commit the Solidity oracle and Foundry differential tests (the original plan)

| Dimension | Assessment |
|-----------|------------|
| Repository contents | Fe plus a Foundry project with the generated verifier and Solidity tests |
| Reader tooling | `fe` and `forge`, plus a forge-std install step |
| Fault localisation | Same step-by-step comparison |
| Regenerating expected values | Possible from the repository, through the committed generator |
| Negative coverage | A shared negative suite on both verifiers, plus one fuzzed proof word |

**Pros:** Everything is reproducible from the repository. Both verifiers run side by side in one EVM.  
**Cons:** Rejected by the project owner: the repository should be Fe only.

### Option C: No oracle, only end-to-end accept/reject

| Dimension | Assessment |
|-----------|------------|
| Repository contents | Pure Fe plus a Noir circuit and scripts |
| Reader tooling | `fe` only |
| Fault localisation | None: a mismatch shows only at the final check |
| Regenerating expected values | Nothing to regenerate beyond the proof |
| Negative coverage | Accept or reject, with no reference to compare against |

**Pros:** Simplest setup. No dependence on any captured value.  
**Cons:** Rejected: in a port of this size, a mismatch could then only be detected at the final check, with no way to locate it.

## Trade-off Analysis

The owner's requirement removes option B. Option C satisfies it but gives up the one thing that makes a staged port workable: knowing which step is wrong. Option A keeps that, and pays with two losses that are recorded below rather than hidden: expected values that cannot be rebuilt from the repository alone, and no fuzzed differential test.

## Consequences

- Easier: a reader verifies the repository with `fe` alone. No `forge` command is needed.
- Easier: the repository is pure Fe plus a Noir circuit and scripts.
- Harder: intermediate expected values cannot be regenerated from the repository alone without recreating the local harness. Their provenance (tool, version, how captured) must therefore be documented.
- Harder: in-EVM fuzzed differential testing against the Solidity verifier is given up in favour of a fixed list of tamper cases.
- Harder: a Fe test cannot choose the caller of a call. The vault's tests use forwarding contracts and the fixed address of the test contract (ADR-0010).
- Settled: the invalid calls are the ones listed in `lib/src/expected.fe`. Nothing is copied from the upstream negative test base, which is marked `UNLICENSED`.
- Settled: `scripts/proof_to_fe.sh` produces the verification-key constants.
- Settled: size and gas are reported next to the reference's figures.
